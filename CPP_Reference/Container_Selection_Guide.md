# C++ 資料結構選用心法

在 C++ 中，選擇正確的資料結構是撰寫高效、可讀且不易出錯程式碼的關鍵第一步。本文件提供了一套心法，幫助你在不同場景下做出最佳選擇。

## 1. 有序 vs. 無序容器的選擇

這是最常見也最重要的決策點之一。

**核心心法**：**如果不需要元素有序，永遠優先考慮使用無序容器。**

- 當你準備寫 `std::set` 時，先問自己：「我真的需要排序嗎？」如果答案是否定的，立即換成 `std::unordered_set`。
- 同理，`std::map` vs. `std::unordered_map` 也應遵循此原則。

### 性能比較

| 容器                             | 主要操作 (插入、刪除、查找) | 底層結構                      |
| :------------------------------- | :-------------------------- | :---------------------------- |
| `set`, `map`                     | `O(log n)`                  | 平衡二元搜尋樹 (通常是紅黑樹) |
| `unordered_set`, `unordered_map` | 平均 `O(1)`, 最壞 `O(n)`    | 雜湊表 (Hash Table)           |

### 何時使用有序容器 (`set`/`map`)

- **需要遍歷時有序**：當你需要按鍵或值的順序迭代容器時。
- **需要範圍查詢**：當你需要快速找到某個範圍內的所有元素時（例如，使用 `lower_bound`, `upper_bound`）。
- **需要自訂複雜比較邏輯**：當元素的比較不是簡單的大小關係，需要自訂比較函式 (functor) 時。
- **需要穩定的性能保證**：當你無法接受 `O(n)` 的最壞情況，需要穩定的 `O(log n)` 保證時。
- **鍵或值沒有好的雜湊函式**：對於自訂型別，如果很難或無法為其設計一個高效的雜湊函式，使用基於比較的 `map` 或 `set` 更為合適。

### 何時使用無序容器 (`unordered_set`/`unordered_map`)

- **追求極致的平均查找速度**：當主要操作是單純的查找、插入和刪除，且希望平均時間複雜度為 `O(1)` 時。
- **不關心元素順序**：當元素的儲存和迭代順序無關緊要時。
- **數據分佈較為均勻**：當你知道數據的雜湊值會分佈得比較均勻，可以有效避免大量雜湊衝突時。

## 2. 其他常用容器選擇心法

- **`vector` vs. `list`**:

  - **預設選 `vector`**。`vector` 的記憶體連續性帶來了極佳的快取局部性 (cache locality) 和高效的隨機存取。
  - 只有在你需要**頻繁地在容器中間插入或刪除大量元素**，且無法接受 `O(n)` 的成本時，才考慮使用 `std::list`。

- **`deque` vs. `vector`**:

  - 當你需要一個行為類似 `vector` 的序列容器，但同時需要**在頭部進行高效的插入和刪除** (`push_front`, `pop_front`) 時，`std::deque` 是最佳選擇。常用於實現滑動窗口或雙端佇列。

- **`priority_queue` vs. 自行排序**:

  - 當你只需要**持續地存取或移除集合中的最大（或最小）元素**，而不需要對整個集合進行完整排序時，使用 `std::priority_queue`。它的 `push` 和 `pop` 操作都比完整排序快得多。

- **`array` vs. C 風格陣列**:
  - **永遠優先使用 `std::array`**。它是一個輕量級的容器封裝，提供了現代 C++ 的便利性（如 `size()`, `begin()`, `end()`），同時保持了與 C 風格陣列相同的性能和記憶體佈局。

## 3. 處理重複元素的考量

在選擇容器時，必須明確資料是否可能包含重複元素，以及如何處理它們。

- **`set` / `unordered_set`**: 自動忽略重複元素，只儲存唯一的副本。
- **`map` / `unordered_map`**: 鍵 (key) 是唯一的。重複插入相同的鍵只會更新其對應的值 (value)。
- **`multiset` / `multimap`**: **明確設計用來處理重複元素**。它們允許儲存多個相同的鍵或值。
- **`map<Key, int>`**: 一種常見且靈活的替代方案，使用 `map` 來手動記錄每個元素的出現次數。

### 總結原則

1. **先問需求**：我需要排序嗎？我需要快速查找嗎？我需要在兩端操作嗎？
2. **再看性能**：`O(1)` 還是 `O(log n)`？平均情況還是最壞情況？
3. **最後考慮特殊情況**：資料有重複嗎？需要自訂比較或雜湊嗎？

遵循這些心法，可以幫助你更自信、更準確地選擇最適合問題的資料結構。
