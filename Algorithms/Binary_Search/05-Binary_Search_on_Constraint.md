# 心法：尋找約束來套用二分搜尋 (Binary Search on Constraint)

## tl;dr

當一個最佳化問題的「可行性」與某個「參數」存在單調關係時（例如，`threshold` 越大，可行解越多），不要直接去計算每個解的成本。

你可以對這個「參數」的可能範圍（Solution Space）進行二分搜尋，來快速定位出「最小/最大可行」的參數值。一個線性的驗證演算法在此僅用於 O(N) 驗證某個 `mid` 值是否可行，真正的最佳化發生在二分搜尋的 O(logK) 過程中。

---

## 1. 問題識別：從「直接最佳化」到「搜尋答案」

很多最佳化問題，直觀想法是：

> 「計算所有可能解的成本，然後取最小/最大值。」

然而，如果問題滿足特定結構，可以直接「搜尋答案」。關鍵的判斷點是：

> 「我能否設計一個 `feasible(k)` 函數，來判斷『答案 `k` 是否可行』？」

如果這個 `feasible(k)` 的結果隨著 `k` 的增減呈現**單調性**，那麼這就是一個可以用二分搜尋解決的問題。

## 2. 單調性觀察 (Monotonicity)

這是套用此心法的基石。你需要觀察問題的性質，例如：

- **觀察**：
  - 如果一個解的成本 `C` 是可行的，那麼任何成本 `C' > C` 的解通常也是可行的（因為條件更寬鬆）。
  - 如果一個解的成本 `C` 是不可行的，那麼任何成本 `C' < C` 的解也必定不可行（因為條件更嚴格）。

這形成了 `F F F... T T T...` 的序列，我們的目標就是找到第一個 `T`。這就是標準的 `lower_bound` 問題，可以用二分搜尋高效解決。

## 3. Solution Space 的建構步驟

### 3.1. 辨識約束 (Identify the Constraint)

- 問題的最佳化目標是什麼？這個目標能否被參數化，作為一個可調整的「約束」？
- _範例_：若目標是「最小化最大成本」，那麼約束就可以是 `cost ≤ k`。

### 3.2. 定義搜尋空間 (Define the Search Space)

- 這個約束參數的理論最小值和最大值是什麼？
- _範例_：成本的搜尋範圍可能是 `[0, max_possible_cost]`。

### 3.3. 設計可行性檢查 (Design the Feasibility Check)

- 給你一個固定的參數 `k`，你如何用 `O(N)` 或接近線性的時間判斷它是否可行？這個檢查必須是高效的。
- `function feasible(k)`：根據 `k` 所設定的約束，執行這個高效的驗證演算法，回傳 `true` 或 `false`。
- _範例_：在圖論問題中，這個檢查可以是一個 **Constraint Connectivity** 問題。在其他問題中，它可能是任何其他可以在線性時間內完成的驗證。

### 3.4. 設定收斂與返回 (Set Up Convergence & Return)

- 使用二分搜尋的 `lower_bound` 模板來找到最小的可行解。

```cpp
  int left = MIN_POSSIBLE_VALUE, right = MAX_POSSIBLE_VALUE;

  while (left <= right) {
      int mid = left + (right - left) / 2;

      if (feasible(mid)) {
          // mid 是一個可行解，但我們想找更小 (更好) 的
          // 所以我們可以安全地捨棄右半邊，繼續在左半邊 [left, mid - 1] 尋找
          // 但是別擔心，最後 left == right，因為不可行，就又跑到 right 右邊 + 1
          right = mid - 1;
      } else {
          // mid 不是可行解，需要放寬條件
          left = mid + 1;
      }
  }

  // 當迴圈結束時，left 就是最小的可行解 (lower_bound)
  return left;
```

- **說明**：當 `while (left <= right)` 迴圈終止時，`left` 指針的位置就是第一個滿足 `feasible(x) == true` 的位置，即 `lower_bound`，這就是我們的答案。

### 3.5. 時間複雜度分析 (Time Complexity Analysis)

- 設 `K` 為搜尋空間的大小 (e.g., `max_value - min_value`)。
- 設 `T_feasible` 為 `feasible()` 函數單次執行的時間複雜度。
- **總時間複雜度** = `O(T_feasible * log(K))`。

這個結構的優美之處在於，它將一個可能非常耗時的最佳化問題，轉化為一個對數級別的迭代，每次迭代內部執行一個相對高效的驗證過程。

## 4. 核心 Takeaway

- **最佳化位置的轉移**：這類問題的「最佳化」發生在**二分搜尋的過程中**，而不是在單次的 `feasible` 驗證過程中。
- **驗證演算法的目的**：`feasible` 函數的唯一目的，是在給定一個固定的 `threshold` 下，快速驗證其**可行性 (feasibility)**。它不關心如何達到最佳解，只回答「是/否」。
- **心法觸發點**：當你發現一個最佳化問題很難直接計算出最佳解時，試著反向思考：「如果我已經知道答案是 `k`，我能否輕易地驗證它是否可行？」如果這個驗證過程是高效的，且答案空間具有單調性，這就是套用此心法的強烈信號。

## 5. 實戰範例：LeetCode 1631. Path With Minimum Effort

這個問題是應用此心法的絕佳範例。

**問題簡述**：在一個 2D 高度圖中，找到一條從左上到右下的路徑，使其路徑上「相鄰格子間的最大高度差」最小。這個「最小的最大高度差」就是我們要找的答案。

### 5.1. 問題識別與轉換

- **直接最佳化 (困難)**：暴力搜尋所有從起點到終點的路徑，記錄每一條路徑的最大高度差，最後找出其中的最小值。這是一個指數級複雜度的解法。
- **搜尋答案 (可行)**：我們可以轉換問題為一個標準的 **Constraint Connectivity** 問題：「是否存在一條路徑，其最大高度差不超過 `k`？」這個問題相對簡單，且答案具有單調性。

### 5.2. 單調性觀察

- 如果一個 `effort = k` 是可行的（能找到路徑），那麼任何 `k' > k` 的 `effort` 也一定是可行的（因為條件更寬鬆，原來的路徑依然有效）。
- 這確認了 `F F F... T T T...` 的模式，可以使用二分搜尋。

### 5.3. 套用建構步驟

1. **辨識約束**：目標是最小化「最大高度差」。我們將其參數化為 `threshold`，約束為 `abs(h1 - h2) ≤ threshold`。
2. **定義搜尋空間**：`threshold` 的範圍是 `[0, 10^6]` (根據題目限制)。
3. **設計可行性檢查 `feasible(threshold)`**：
   - **問題**：給定 `threshold`，是否存在一條從左上到右下的路徑，每一步高度差都 `≤ threshold`？
   - **解法**：這是一個標準的 **Connectivity** 問題，可用 DFS 或 BFS 在 `O(R*C)` 時間內解決。
4. **設定收斂與返回**：
   - 在 `[0, 10^6]` 範圍內進行二分搜尋。
   - `if (feasible(mid))` 為真，表示 `mid` 可行，嘗試更小的解，`right = mid - 1`。
   - `if (feasible(mid))` 為假，表示 `mid` 不可行，須放寬條件，`left = mid + 1`。
   - 迴圈結束後，`left` 就是最小的可行 `effort`。

### 5.4. 時間複雜度分析

- **二分搜尋**：搜尋空間大小為 `K` (約 `10^6`)，複雜度為 `O(log K)`。
- **可行性檢查**：每次檢查需要對 `R x C` 的網格進行一次完整的圖遍歷，複雜度為 `O(R * C)`。
- **總複雜度**：`O(R * C * log K)`。

這個例子完美展示了如何將一個看似複雜的最佳化問題，拆解成一個「二分搜尋框架」和一個「簡單的可行性檢查函數」。
