# 模擬（Simulation）解題心法

**以程式表示系統狀態，依指定規則與順序更新，求出過程中的觀察結果或最終結果。**
這是綜合教材整理的工作定義，不是某本書的逐字定義。Simulation 是解題方法，沒有固定的資料結構或複雜度；可以搭配 Stack、Queue、Heap，也可以利用數學規律減少執行步驟。

## 🧠 核心哲學：把規則變成可驗證的狀態轉換

模擬的重點是**每次更新後，程式狀態都忠實代表規則所描述的系統**。
先建立正確的直接模擬，再分析哪些資訊不必保存、哪些過程可以省略。不是每題都需要進一步優化。

```text
定義觀察目標 → 選擇狀態 → 定義一步 → 按正確順序更新 → 觀察結果／判斷停止
```

例如一台沿軌道移動的機器：若要求最終位置，需保存位置與方向；若要求曾到達的最遠位置，還要維護歷史最大值。**狀態是否足夠，取決於目標。**

## 1. 🧩 寫程式前的五個設計問題

| 問題 | 必須說清楚的內容 |
|---|---|
| **要觀察什麼？** | 最終結果、途中峰值、首次發生時間，還是能否到達？ |
| **要記住什麼？** | 哪些資訊會影響下一步或答案：位置、方向、時間、資源、未完成工作？ |
| **一步是什麼？** | 一個指令、一個時間步、一輪同步更新，還是一個事件？ |
| **如何更新？** | 讀哪個版本、何時寫入、同時事件如何排序、何時記錄答案？ |
| **何時停止？** | 輸入耗盡、目標達成、無事可做，或已能證明後續不會改變答案？ |

**口訣：目標 → 狀態 → 一步 → 順序 → 停止。**
只保存會影響未來或答案的資訊；例如輸出只按群組排列時，不必建立包含空格的完整二維版面。

## 2. 更新語義：依序生效，還是同時生效？

### Sequential Update：後一步看得到前一步的結果

例如 A 向 B 倒水，再由 B 向 C 倒水，第二次必須使用**收到水之後的 B**。
每次倒水量為 `min(來源現有量, 目的地剩餘容量)`；兩邊使用同一個轉移量更新，才能維持總量守恆。

### Synchronous Update：同一輪只能讀取上一輪

例如規則是 `nextA = oldB`、`nextB = oldA`，初始 `(A,B) = (1,0)`，下一輪應為 `(0,1)`。
若依序寫 `A = B`、`B = A`，會得到 `(0,0)`：第二次讀到了新值，已經改變規則。

**先算下一輪，再一起提交。** 可用獨立的 next buffer；若原地編碼，也必須能區分舊值與新值。
同步語義不要求真的平行執行，但要求讀取的版本一致。

### 同時事件：先定義時間邊界，再定義處理順序

資源占用區間若採 `[start,end)`，在 `t` 結束的工作不再占用 `t`，可讓同時開始的工作接手。
若同時事件可交換且只觀察整批處理後的結果，可以合併；否則需明定平手順序，或先計算整批的共同結果。**不能讓容器的偶然順序決定語義。**

## 3. 模擬粒度：什麼時候才需要做事？

| 推進方式 | 適合情況 | 必須確認 |
|---|---|---|
| **按指令／步驟** | 每個操作都可能影響結果 | 每一步的合法性、邊界與觀察時機 |
| **Time-driven** | 規則按固定時間步定義，或需要數值近似 | 時間步長的意義；連續系統要分析誤差與漏事件風險 |
| **Event-driven** | 重要變化只發生在可識別的事件時刻 | 下一事件如何取得；跳過的區間如何影響答案 |

例如工作在時間 5 結束，下一次到達在 100，系統空閒時可以直接跳到 100。
但若答案是累積等待時間、距離或面積，**跳過時間時仍須計入該段貢獻**。
事件之間不一定完全靜止；也可能按已知規律演進，可直接算到下一個事件。

事件預先已知時，可排序後掃描；執行中會產生新事件時，常用 Heap 取最早者。
預測事件若會因其他操作失效，需驗證版本或有效性；不能只因它排在最前面就執行。

## 4. 省略模擬：先證明規律，再跳過過程

| 方法 | 省掉什麼 | 成立前提 |
|---|---|---|
| **週期與直接映射** | 反覆執行相同動作 | 對所求資訊，已證明可重複的規律 |
| **完整狀態循環** | 再走一遍已知的狀態序列 | 同狀態的未來演化相同；外部輸入階段也要一致 |
| **不變量／可達性條件** | 搜尋或模擬大量操作順序 | 條件若用來判定可達，需證明必要且充分 |

例如位置在 `0..h` 間每次移動一格、碰端點反向，且從 0 向上出發（`h > 0`）：

```text
位置：0, 1, ..., h, h-1, ..., 1, 0, ...
週期 C = 2h；令 t = 步數 mod C
位置 = t       （t <= h）
位置 = C - t   （t > h）
```

這是**找週期 → 取餘定位 → 分段映射**。若只求某一步的位置，可以直接算；若必須輸出每一步，仍要支付輸出成本。`h = 0` 要另外處理，不能模零。
循環偵測也不能只比位置：方向、剩餘資源或指令階段不同，都可能導致不同的未來。跳過循環時，歷史累積量仍要正確更新。

完整狀態的循環偵測、時間標記與取餘跳躍模板，見 [Cycle Detection + Fast Forwarding](02-Cycle_Detection_and_Fast_Forward.md)。

## 5. 正確性與成本：忠實執行，也要保證能結束

**Loop invariant：每輪開始時，已處理部分的效果已正確反映在狀態中；未處理工作仍完整保留。**
依序確認初始化成立、單步更新保持此性質、停止時能推出所求結果。
再指出進展量：剩餘指令減少、未處理事件減少，或抵達有界的終止時間。**時間增加本身不保證終止**；持續產生事件的系統可能永遠執行。

| 執行方式 | 時間成本 | 額外空間 |
|---|---|---|
| T 步、每步成本 c | `O(Tc)` | 依所保存的狀態計算 |
| N 個單位，同步更新 T 輪 | `O(TN)` | 一份 next buffer 通常為 `O(N)` |
| E 個已知事件，排序後常數成本更新 | `O(E log E)`；已排序則 `O(E)` | 儲存事件通常為 `O(E)` |
| E 次事件處理，每次常數次 Heap 操作 | `O(E log(Q+1))`，Q 為最大佇列大小 | `O(Q)`，另計系統狀態 |

事件產生、驗證與更新若不是常數成本，要另外計入；容器物件、空桶、暫存與輸出也要分清楚計算。

## ✅ 實作前檢查

- [ ] 狀態足以決定下一步與答案，沒有保存不必要的版面細節。
- [ ] 已定義一步、讀寫版本、同時事件順序，以及觀察答案的時機。
- [ ] 有停止條件與進展理由；無法完成時也能正確結束。
- [ ] 跳過時間或週期時，沒有漏掉途中事件與累積貢獻。
- [ ] 用空輸入、單一步驟、邊界轉向、同時事件、新舊值互換測試模型。
