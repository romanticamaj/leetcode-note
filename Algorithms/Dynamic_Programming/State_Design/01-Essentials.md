# DP 狀態設計的兩大基石

本文檔闡述了設計高效、準確的 DP 狀態所需遵循的兩大核心原則。掌握這些原則，是從暴力回溯平滑過渡到動態規劃的關鍵。

---

## 基石一：劃清「問題」與「選擇」的界線

在思考 DP 狀態時，首要任務是嚴格區分以下兩個概念：

### 1. 問題狀態 (Problem State)

- **本質：** 定義一個**唯一子問題**所需的最小變數集。
- **來源：** 通常直接來自原始問題的 **輸入**，例如 `index`（處理到哪個元素）或 `capacity`（背包剩餘容量）。
- **作用：** 構成 DP `cache` 或 `table` 的維度，是 Memoization 或 Tabulation 的 `key`。`dp[index][capacity]` 代表一個獨一無二的子問題的解。

### 2. 決策空間 (Choice Space)

- **本質：** 在某個特定的「問題狀態」下，可以採取的**行動**。
- **例子：** 對於 `nums[index]`，可以「選」或「不選」；在當前位置，可以往「左」或「右」走。
- **作用：** 決策是在狀態轉移中被探索和消耗的，**通常不應**成為 DP 狀態的一部分。`dp[state] = max(choice1_result, choice2_result)`。

> **核心心法：** 狀態定義應專注於「問題本身」，而非「解決問題的過程中的選擇」。這是簡化狀態設計的第一步。

---

## 基石二：識別並納入「狀態依賴性」

這是原則一的關鍵例外，也是 DP 狀態設計中最精妙的部分。

> **黃金法則：** 當「過去的決策」會限制或影響「未來的決策空間」時，這個決策所產生的「後果」就必須被納入狀態中。

換句話說，如果我們需要一個「記憶」來追蹤過去某個決策的影響，這個「記憶」就必須成為狀態的一部分。

### 設計信號：固定的選擇狀態

- **信號：** 當一個問題的「選擇」可以被歸納為 `k` 個固定的、互斥的狀態時（例如「持有/未持有」、「搶/不搶」、「冷凍/自由」），這就是一個強烈的信號。
- **行動：** 我們需要在 DP 狀態中**增加一個維度**來區分這些情況。這個新增的維度，其本質就是將「決策的後果」記錄下來。
- **範例：**
  - **股票買賣：** 「當前是否持有股票」(`buying/selling`) 必須成為狀態，演變為 `dp(day, has_stock)`。
  - **打家劫舍：** 「前一家是否被搶」隱含在狀態轉移中，更顯式的狀態是 `dp(index, prev_robbed)`。
- **實現連結：**
  > 這種狀態設計思想，在實現時，通常會表現為 [`03-DP_Recurrence_Design_Patterns.md`](./03-DP_Recurrence_Design_Patterns.md) 中描述的「狀態機依賴」模式（如多表法或雙遞迴）。

#### 實踐工具：「試金石」測試

當你不確定一個變數 `k` 應該是「問題狀態」的一部分，還是僅僅是「路徑依賴」的累加器時，可以使用此測試：

> **審視你的遞迴函式 `solve(index, k, ...)`，問自己：「固定 `index`，只改變 `k`，是否會導致 `solve` 函式返回的『最優解』可能不同？」**

- **如果答案是「是」：** `k` 是**狀態定義參數**，必須納入 Cache Key。
- **如果答案是「否」：** `k` 是**路徑依賴參數**，不應納入 Cache Key。

---

## 總結

1. **定義問題：** 首先，用最少的變數定義「子問題」本身。
2. **檢查依賴：** 接著，審視你的「決策」，如果某個決策會改變遊戲規則（影響後續決策），那麼這個決策的「後果」就需要被提升為狀態的一部分。
3. **驗證狀態：** 最後，使用「試金石」測試來驗證狀態變數的必要性。
