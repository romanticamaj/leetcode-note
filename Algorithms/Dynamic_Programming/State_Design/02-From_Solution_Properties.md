# DP 狀態設計心法：從「解的性質」決定「狀態維度」

動態規劃的威力源於其對「狀態」的精準定義。然而，最困惑人的也往往是：「我的狀態到底該包含哪些資訊？」一個問題是需要 `dp[target]` 的一維狀態，還是 `dp[index][target]` 的二維狀態，其決策源頭並非來自 DP 本身，而是來自於對「問題解的性質」的深刻理解。

本文件提供一個泛化的思維框架，幫助你從問題的本質出發，系統性地設計出最簡潔且正確的 DP 狀態。

---

## tl;dr

> **透過分析「解的性質」（最優值 vs. 計數、組合 vs. 排列），可以判斷是否需要追蹤唯一路徑。若不需追蹤，則狀態維度通常可以被壓縮，從而簡化 DP 設計。**

---

## 核心決策鏈：解的性質 → 狀態設計 → 演算法實現

這是一條清晰的因果鏈：

> **解的性質 (Solution Properties)** → **窮舉搜索設計 (Exhaustive Search Design)** → **狀態定義 (State Definition)** → **DP 實現 (DP Implementation)**

我們必須從鏈的源頭開始思考。

### 第一步：分析問題所求為何？(What does the problem ask for?)

首先，將問題的最終輸出歸結為三類之一：

1. **最優值 (Optimization) / 可行性 (Feasibility):**

   - **關鍵詞：**「最少」、「最多」、「最大」、「最小」、「能否組成」。
   - **核心特徵：** 通常不關心達成最優值的方式有幾種或具體方式是什麼。`[1, 2, 2]` 和 `[2, 1, 2]` 都能組成 5，它們在最優值問題中是等價的。
   - **初步結論：** 這是**狀態壓縮**潛力最大的問題類型。

2. **計數 (Counting):**

   - **關鍵詞：**「總共有幾種方法」、「計算所有可能性」。
   - **核心特徵：** 必須嚴格區分不同的「方法」。此時，下一個問題變得至關重要。

3. **列舉 (Enumeration):**
   - **關鍵詞：**「找出所有組合」、「返回所有路徑」。
   - **核心特徵：** 必須記錄完整的決策路徑。
   - **初步結論：** 這本質上是回溯法，DP (Memoization) 只能作為剪枝優化，通常無法大幅壓縮狀態。

### 第二步：定義「解」的獨立性 — 組合 vs. 排列

這是決定狀態是否需要包含 `index` 的**關鍵分水嶺**。

- **組合 (Combination): 解的元素順序無關**

  - **定義：** `[1, 2, 2]` 和 `[2, 2, 1]` 被視為**同一種**解。
  - **窮舉設計策略：** 為了避免重複計算，搜索時必須引入**人為的順序**。標準做法是：「當考慮完 `candidate[i]` 後，接下來只考慮 `candidate[i]` 或 `candidate[i+1:]` 的元素，絕不回頭考慮 `candidate[i-1]`」。
  - **狀態設計結果：** 這個「人為順序」的約束，自然地要求將 `index` 作為狀態的一部分，以告知搜索「我現在該從哪個候選者開始考慮？」。因此，狀態通常被設計為 `dp(index, target)`。

- **排列 (Permutation): 解的元素順序有關**
  - **定義：** `[1, 2, 2]` 和 `[2, 2, 1]` 被視為**不同的**解。
  - **窮舉設計策略：** 在每一步決策時，都可以從**所有**候選者中進行選擇。沒有必要為了去重而引入順序。
  - **狀態設計結果：** 因為每一步的決策空間都一樣（都是從完整的候選者集合中選），所以「當前考慮到哪個 `index`」是不重要的。唯一決定子問題的是「還剩下多少目標值」。因此，狀態可以被簡化為 `dp(target)`。

### 第三步：綜合決策 — 設計你的狀態

結合前兩步的分析，我們可以得出一個狀態設計的決策矩陣：

| 問題所求            | 解的性質：組合 (順序無關)                                                                                                                                                                    | 解的性質：排列 (順序有關)                                                                                                             |
| :------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------ |
| **最優值 / 可行性** | **狀態可壓縮為 `dp(target)`**。<br>因為 `[1,2]` 和 `[2,1]` 是等價的，我們不需要 `index` 來區分它們。窮舉時可以像「排列」一樣，在每一步都考慮所有候選者，因為最優值會自然地覆蓋掉非最優路徑。 | **狀態為 `dp(target)`**。<br>問題本身就允許重複路徑，且每條路徑都可能貢獻最優解。                                                     |
| **計數**            | **狀態必須是 `dp(index, target)`**。<br>必須用 `index` 來強制一個枚舉順序，以確保每種「組合」只被計算一次。                                                                                  | **狀態可簡化為 `dp(target)`**。<br>因為每種「排列」都要計算，所以不需要 `index` 來去重。`dp(target)` 的遞迴關係會自然地探索所有排列。 |
| **列舉**            | **狀態必須是 `dp(index, target, path)`**。<br>這就是標準的回溯法，用 `index` 去重。                                                                                                          | **狀態是 `dp(target, path)`**。<br>這也是回溯法，但不需 `index` 去重。                                                                |

---

## 總結心法

1. **先看問題求什麼**：是「最優值」，還是需要區分不同解的「計數/列舉」？

   - 如果是「最優值」，你就有極大的概率可以將狀態壓縮到最簡形式（如 `dp(target)`），因為你不需要關心路徑的唯一性。

2. **再看解是否關心順序**：是「組合」還是「排列」？
   - 如果是「組合」（不關心順序），並且你需要「計數/列舉」，那麼你**必須**在狀態中加入 `index` 來強制枚舉順序，以避免重複。
   - 如果是「排列」（關心順序），那麼你**不需要** `index` 來去重，狀態可以更簡潔。
