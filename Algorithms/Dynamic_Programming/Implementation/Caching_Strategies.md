# DP 快取策略：Memoization 的實現與權衡

在 Top-Down DP 中，快取 (cache) 是核心，它負責儲存子問題的解以避免重複計算。如何設計和管理這個快取，會直接影響程式碼的正確性、可讀性和效能。

本文件將探討幾種常見的快取實現策略，並總結在不同場景下的最佳實踐。

---

## 1️⃣ 快取的範圍 (Scope) 與生命週期

快取的「可見範圍」和「存在時間」是設計時首先要考慮的問題。

### 策略一：透過參數傳遞 (Passing as a Parameter)

這是最安全、最推薦的作法，特別是在 LeetCode 或其他競賽平台。

- **實現：** 將快取作為遞迴函式的一個參數，通常以**引用 (by reference)** 方式傳遞，以避免不必要的複製。
- **範例：**

```cpp
  int solve(int n, std::unordered_map<int, int>& cache);
```

- **優點：**
  - **生命週期清晰：** 快取的生命週期由呼叫者 (caller) 控制，每次主函式呼叫都會建立一個全新的、乾淨的快取。
  - **無副作用：** 函式是無狀態的，不會受到先前呼叫的影響，完美適用於多測試案例的環境。
- **缺點：**
  - 函式簽名稍長。

### 策略二：使用類別成員變數 (Member Variable)

當解法被封裝在一個類別中時，這是一個常見且清晰的作法。

- **實現：** 快取是類別的一個私有成員變數。
- **範例：**

```cpp
  class Solution {
  private:
      std::unordered_map<int, int> cache;
  public:
      int solve(int n) {
          // ...
      }
  };
```

- **優點：**
  - **職責分離：** 函式本身不需管理快取，其職責更單純。
  - **自動重置：** 在 LeetCode 這類平台，每次測試案例都會建立一個新的 `Solution` 物件，因此成員變數會被自動重置。
- **缺點：**
  - 需要將解法封裝在類別中。

### 策略三（陷阱）：使用函式靜態變數 (Function Static Variable)

**這是一個應極力避免的陷阱，尤其是在競賽平台。**

- **實現：** `static` 變數在函式的多次呼叫之間會保持其值。
- **問題：** `static` 變數只會被初始化一次。在 LeetCode 中，多個測試案例會連續執行，第二次呼叫函式時，`static` 快取中會殘留上一個案例的資料，導致結果錯誤。
- **結論：** 除非你非常確定函式只會被呼叫一次，或你有手動重置 `static` 變數的機制，否則絕不應該使用此方法來做 DP 的快取。

## 2️⃣ 快取資料結構的選擇

選擇 `unordered_map` 還是 `vector`，取決於問題狀態的特性。

| 特性             | `std::unordered_map` (雜湊表)                                                           | `std::vector` (或陣列)                                                        |
| :--------------- | :-------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------- |
| **存取時間**     | 平均 `O(1)`                                                                             | `O(1)`                                                                        |
| **狀態空間**     | 適用於**稀疏 (sparse)** 或**非連續**的狀態。例如，狀態可能是 `(index, remaining_sum)`。 | 適用於**密集 (dense)** 且**連續**的整數狀態。例如，狀態是 `0` 到 `n` 的索引。 |
| **空間開銷**     | 每個條目都有額外開銷 (overhead)。                                                       | 空間開銷低，但需要一次性分配所有可能的狀態空間。                              |
| **記憶體局部性** | 較差 (Poor memory locality)。                                                           | **較好 (Good memory locality)**，可能帶來輕微的效能優勢。                     |
| **使用複雜度**   | 簡單，直接 `cache[key] = value`。                                                       | 需要管理索引和大小，並可能需要一個額外的值來標記「未計算」狀態。              |

### 總結與常用實踐

1. **首選 `unordered_map`：**

   - 在大多數情況下，`unordered_map` 是最靈活、最不易出錯的選擇。你不需要擔心狀態是否連續，或是狀態的最大值是多少。

2. **何時使用 `vector`：**
   - 當你明確知道 DP 的狀態是一個**有界的、連續的整數**時（例如，`dp[i]` 中的 `i` 從 `0` 到 `n`），使用 `vector` 是更高效的選擇。
   - 使用 `vector` 時，通常需要初始化一個特殊值（如 `-1`）來表示該狀態尚未被計算。

### 最佳實踐總結

> **在 LeetCode 或類似環境中，最穩健的 Top-Down DP 快取策略是：將 `std::vector` 作為參數，以引用方式傳遞給遞迴函式。**

```cpp
class Solution {
public:
    int problem(int n) {
        std::vector<int> cache(n, -1);
  
        return solve(0, cache);
    }

private:
    int solve(int i, std::vector<int>& cache) {
        if (boudary_condition(i)) {
            return base_case_solution;
        }

        if (cache[i] == -1) {
            cache[i] = solve(i + 1, cache) + solve(i + 2, cache);
        }

        return cache[i];
    }
};
```
