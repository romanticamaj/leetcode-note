# 動態規劃的系統化解題框架

本文件旨在闡述一個系統性的思維框架，用以解決動態規劃 (Dynamic Programming) 問題。它將引導你從一個基礎的暴力解法開始，逐步優化，最終推導出高效的 DP 解。

---

## 第一章：DP 的核心哲學

在開始解題前，必須先理解動態規劃的兩個核心前提，它們是所有 DP 解法的基石。

### 1.1 最優子結構 (Optimal Substructure)

- **定義：** 一個問題的全域最優解，可以由其子問題的最優解構成。
- **核心判斷：** 當前狀態的最優解，是否能透過「當前選擇」與「後續子問題的最優解」組合而成？

### 1.2 重疊子問題 (Overlapping Subproblems)

- **定義：** 在遞迴求解的過程中，許多相同的子問題會被反覆計算。
- **核心目的：** DP 的核心目的就是透過快取 (caching) 或列表 (tabulation) 來避免對子問題的重複計算。

---

## 第二章：DP 的推導路徑：一個起點，兩條哲學

與其視為一條線性的路徑，不如將 DP 的推導過程看作一個**分岔路**。所有問題都從同一個起點開始，但在優化時，可以選擇兩條截然不同的哲學路徑。

### 2.1 起點：暴力回溯 (Brute-Force Backtracking)

- **目標：** 正確性優先於效能，用純遞迴枚舉所有可能性。
- **實現：** 探索所有決策分支，並在遞迴終點**收集 (collect)** 結果。
- **產出：** 一個能運作但效率極低的基準解 (baseline)，是所有 DP 優化的基礎。

### 2.2 分岔路：兩種 DP 優化哲學

#### 路徑 A：由上而下 DP (Top-Down DP / Memoization)

這是對「暴力回溯」最直觀的優化。

- **核心思想：** 我寫的暴力回溯函式會重複計算，我只需要加個快取 (cache) 來記住結果。
- **關鍵轉變：** 從 `collect` 思維轉向 `combine` 思維，讓遞迴函式 `return` 子問題的最優解。
- **優點：** 從回溯法過渡最為自然，程式碼結構改動小。
- **挑戰：** **狀態唯一性與 Cache Key 設計**，這是此路徑最容易出錯的環節。

#### 路徑 B：由下而上 DP (Bottom-Up DP / Tabulation)

這是一條需要**重新設計**的、更高效的路徑。

- **核心思想：** 忘掉遞迴，直接從最小的子問題開始，像蓋大樓一樣，一步步建構出最終的解。
- **關鍵轉變：** **重新定義狀態的物理意義**。這不再是翻譯遞迴函式，而是全新的設計。
- **優點：** 效能通常更佳（無遞迴開銷），且是通往最終空間優化的必經之路。

### 2.3 最終優化：空間優化 (Space Optimization)

- **觸發條件：** 通常在 **Bottom-Up** 的基礎上進行。
- **觀察：** 如果 `dp[i]` 的計算只依賴於前 `k` 個狀態，則無需儲存整個 DP 表。
- **實現：** 使用固定數量的變數（滾動陣列）來達成此目的。

## 第三章：實戰心法：常見陷阱與修正策略

理論是清晰的，但實作過程充滿了陷阱。本章節聚焦於解決這些最常見的卡點。

### 3.1 陷阱一：Backtracking 未窮舉所有決策

- **症狀：** 解法遺漏了某些正確答案。
- **核心問題：** 在每個狀態節點，沒有劃分出所有可能的、互斥的選擇。
- **修正心法：**
  > **枚舉所有互斥且完備的選擇 (MECE Principle):**
  > 在每個狀態節點，必須劃分出所有可能的、不重疊的決策，確保它們共同構成了完整的選擇空間。常見模式有：
  >
  > - **「選/不選」模式：** 用於子集/子序列問題。
  > - **「遍歷選項」模式：** 用於組合/構成問題。

### 3.2 陷阱二：Top-Down 的 Cache Key 未包含完整狀態

- **症狀：** Memoization 產生錯誤結果。
- **核心問題：** 忽略了除了主要進度變數（如 `index`）之外，還有其他「約束變數」會影響子問題的解。
- **修正心法：**
  > **採用「狀態唯一性試金石」**：審視回溯函式的每個參數，並提問：「固定 `index`，只改變這個參數，是否會影響函式的返回值？」
  >
  > - **會** -> 此參數是**狀態定義參數**，必須納入 Cache Key。
  > - **不會** -> 此參數是**路徑依賴參數**，不應納入 Cache Key。

### 3.3 陷阱三：Bottom-Up 直接翻譯 Top-Down 的遞迴關係

- **症狀：** Bottom-Up 的 `dp` 表更新邏輯錯誤。
- **核心問題：** Top-Down 和 Bottom-Up 的狀態定義常常是**相反**或**不同**的。
  - _Top-Down 視角：_ 「從我這裡**出發**，未來最好的結果是什麼？」
  - _Bottom-Up 視角：_ 「要**到達**我這裡，可以從哪些過去的已知最佳狀態轉移而來？」
- **修正心法：**
  > **重新定義狀態，而非翻譯公式：** 在設計 Bottom-Up 解法時，必須忘掉 Top-Down 的函式簽名，專注於 `dp[i]` 的物理意義，並思考它與 `dp[j]` (j < i) 的關係。

---

## 第四章：總結

> **「DP 的本質是：識別最優子結構與重疊子問題，精確定義狀態與基礎案例，選擇 Top-Down 或 Bottom-Up 路徑進行實現，並在需要時尋求空間優化。」**
