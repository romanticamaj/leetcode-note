# 回溯法：狀態設計與解構建 (State and Solution Design)

當我們掌握了回溯法的基本模板後，要寫出更優雅、高效的程式碼，關鍵在於深入理解兩個核心設計支柱：**狀態管理 (State Management)** 與 **解構建 (Solution Construction)**。

這兩個概念是正交的，可以獨立思考，但它們共同決定了回溯演算法的最終形態與效率。

---

## 第一支柱：狀態管理 (State Management) - 追蹤路徑

狀態管理的目標是：在遞迴的每一步，如何有效地表示「已經做出的選擇」與「還可以做的選擇」。

### 核心原則：劃分「已決策 (Decided)」與「待決策 (Undecided)」空間

所有狀態管理技巧的本質，都是在想辦法劃分問題的選擇空間。在遞迴的每一層，我們的任務是：

1. 從「待決策 (`Undecided`)」空間中挑選一個候選者。
2. 將其加入「已決策 (`Decided`)」空間 (即加入當前路徑)。
3. 遞迴進入下一層。

### 黃金法則：狀態修改的對稱性

在回溯的「`Choose`, `Explore`, `Unchoose`」三部曲中，狀態的修改與還原必須是**完全對稱、可逆的成對操作**。這確保了當你從一個遞迴分支返回時，狀態能完美地恢復，讓 `for` 迴圈可以正確地探索下一個分支。

**常見的對稱操作：**

| 做出選擇 (Choose)        | 撤銷選擇 (Unchoose) (對稱還原)            |
| :----------------------- | :---------------------------------------- |
| `path.push_back(x)`      | `path.pop_back()`                         |
| `visited[i] = true`      | `visited[i] = false`                      |
| `swap(nums[i], nums[j])` | `swap(nums[i], nums[j])` (再次交換以還原) |
| `count--`                | `count++`                                 |
| `current_sum += x`       | `current_sum -= x`                        |

確保你的每一次狀態修改都有一個對應的、精確的還原操作，是寫對回溯演算法的基礎。

### 狀態管理模式

以下是實現「劃分空間」的幾種常見模式：

#### 模式一：使用輔助空間 (e.g., `visited` 陣列)

- **作法**：使用一個額外的 `bool` 陣列 `visited` 來追蹤哪些元素已經被選入當前的路徑中。
- **優點**：邏輯非常直觀，直接模擬了「這個選項我用過了」的概念。
- **缺點**：需要 `O(N)` 的額外空間。

#### 模式二：原地操作 (e.g., `swap` 技巧)

- **作法**：這是更高階的技巧，不依賴額外的追蹤陣列，而是透過直接修改輸入資料的結構來隱性地劃分「已決策」和「待決策」空間。經典範例是排列問題中的 `swap` 技巧。
- **運作方式**：使用 `index` 作為「已決策」集合 `[0, index-1]` 的邊界。`for` 迴圈遍歷「待決策」集合 `[index, n-1]`，將每個候選者輪流交換到 `index` 位置上進行決策。
- **心法**：`swap` 操作是在固定當前決策點 (`index`) 的同時，將整個「待決策」空間的元素輪流推上該決策點的方式。這個技巧將輔助空間複雜度降至 `O(1)` (不計遞迴堆疊)。

#### 反模式三：傳遞子集合 (Passing Sub-collections by Value)

- **作法**：在每次遞迴呼叫時，只傳遞「尚未被選擇」的元素集。
- **為何是反模式 (在 C++)**：雖然理論上很清晰，但在 C++ 這類語言中極不實用。在遞迴的每一層都複製容器 (如 `std::vector`) 的成本過高，會導致時間和空間複雜度爆炸。在面試和競賽中應優先考慮模式一和模式二。

## 第二支柱：解構建 (Solution Construction) - 收集結果

解構建的目標是：在遞迴的過程中，如何以及在何處收集所有找到的有效解。核心的區別在於**解是在決策樹的何處被認定的**。

### 建構策略

#### 策略一：在葉節點收集解 (Solutions at Leaf Nodes)

- **判斷時機**：當一個**完整的決策路徑**（通常是從根到葉）才構成一個有效的解時，採用此策略。部分路徑本身不是解。
- **作法**：在遞迴的**終止條件 (`base case`)** 內部，當你確認一個完整的解已經形成時，才將當前的 `path` 複製一份並存入 `results` 容器。
- **適用問題**：
  - **排列 (Permutations)**: `path` 的長度達到 `n`。
  - **組合 (Combinations)**: `path` 的長度達到 `k`。
  - **N-皇后 (N-Queens)**: 已經成功放置了 `n` 個皇后。

#### 策略二：在所有節點收集解 (Solutions at All Nodes)

- **判斷時機**：當**決策過程中的每一個中間步驟（部分路徑）本身就是一個有效的解**時，採用此策略。
- **作法**：在遞迴函式的**入口處**，就立刻將當前的 `path` 複製一份並存入 `results`。這確保了從空集到最長路徑的所有中間狀態都被收集。
- **適用問題**：
  - **子集 (Subsets / Power Set)**: `[]`, `[1]`, `[1, 2]` 等都是合法的子集。

### 替代模式：分治法 (Divide and Conquer)

需要注意的是，還存在一種看似相似但本質不同的遞迴模式：

- **作法**：遞迴函式**返回 (`return`)** 一個包含其所有子問題解的容器。上層函式接收來自子節點的解集合，並將其組合、加工成自己的解集再返回。
- **本質**：這更偏向於**分治法 (`Divide and Conquer`)** 的思想。它不是在維護一個全域的 `path`，而是在每一層獨立地建構解。
- **適用問題**：
  - **Unique Binary Search Trees II**: 遞迴地產生所有可能的左子樹和右子樹，然後在當前層將它們組合起來。

## 交互作用：剪枝 vs. 最終驗證

`is_promising` 檢查 (剪枝) 和最終的「解構建」步驟緊密相關。理解它們的關係，可以幫助我們設計出更簡潔高效的演算法。

### 兩個檢查點：`is_promising` 與 `base case`

1. **`is_promising` 檢查 (剪枝)**

   - **角色**：驗證「當前部分解是否合法，且有潛力擴展成最終解」。
   - **發生時機**：通常在 `for` 迴圈內部，選擇一個候選者之後、遞迴呼叫之前。

2. **解構建檢查 (驗證)**
   - **角色**：檢查「目前狀態是否已經達成一個完整解」。
   - **發生時機**：通常在遞迴函式的入口，作為終止條件 (`base case`)。

### 權衡：轉移驗證邏輯

關鍵的設計問題是：**我是否可以足夠信任我的剪枝檢查，從而讓我的 `base case` 變得微不足道？**

- **情境一：嚴格剪枝，簡單 `base case`**
  - **思想**：`is_promising` 檢查足夠強大，保證任何能到達 `base case` 的路徑都必然是合法的。正確性在每一步都被增量地保證。
  - **結果**：`base case` 的檢查變得非常簡單 (例如 `if (path.size() == k)`)，無需昂貴的、對整個路徑的再次驗證。
  - **範例 (N-Queens)**：`is_promising` 確保了皇后之間從不互相攻擊。因此，當 `row == n` 時，我們*知道*這是一個合法解，可以直接加入結果，無需重新檢查棋盤。

- **情境二：寬鬆剪枝，複雜 `base case`**
  - **思想**：`is_promising` 檢查很寬鬆，甚至不存在。大量的驗證工作被推遲到一個完整的路徑被構建出來之後。
  - **結果**：`base case` 必須對整個 `path` 進行可能很昂貴的檢查，以確定它是否是一個有效的解。
  - **範例 (Palindrome Partitioning)**：我們可以將字串以多種方式分割。只有在 `base case` (整個字串都被分割完畢) 時，我們才能遍歷 `path` 中的所有子字串，檢查它們是否都是回文。

### 指導原則：信任你的剪枝

一個設計良好的 `is_promising` 函式，可以將驗證工作分散到遞迴的每一步，從而讓 `base case` 的最終解構建步驟變得極其簡單和高效。

## 總結：一個統一的設計框架

在設計回溯演算法時，你可以將這兩個支柱及其交互作用作為獨立的設計維度來考慮：

1. **狀態管理 (State Management)**：我應該如何最有效地追蹤選擇？是 `visited` 陣列的清晰性值得額外空間，還是 `swap` 技巧的效率更重要？
2. **解構建 (Solution Construction)**：解在何處被最終確認？是在決策樹的葉節點 (如 Permutations)，還是在每個節點 (如 Subsets)？或者這是一個應該 `return` 結果的 `Divide and Conquer` 問題？
3. **交互作用 (The Interplay)**：我可以將多少驗證工作推入我的 `is_promising` 檢查中？在探索過程中驗證得越多，在到達目的地 (`base case`) 時需要做的工作就越少。

清晰地分離這些概念，能讓你更有條理地設計出簡潔、高效且正確的回溯程式碼。
