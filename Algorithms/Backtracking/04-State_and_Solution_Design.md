# Backtracking: State Design and Solution Construction

當我們掌握了回溯法的基本模板後，要寫出更優雅、高效的程式碼，關鍵在於深入理解兩個核心設計決策：**狀態管理 (State Management)** 與 **解構建 (Solution Building)**。

這兩個概念是正交的，可以獨立思考，但它們共同決定了回溯演算法的最終形態與效率。

---

## 狀態管理的策略 (State Management)

狀態管理的目標是：在遞迴的每一步，如何有效地表示「已經做出的選擇」與「還可以做的選擇」。

### 核心原則：劃分「已決策 (Decided)」與「待決策 (Undecided)」空間

所有狀態管理技巧的本質，都是在想辦法劃分問題的選擇空間。在遞迴的每一層，我們的任務是：

1. 從「待決策」空間中挑選一個元素。
2. 將其加入「已決策」空間。
3. 遞迴進入下一層。

#### 對稱性原則：狀態的修改與還原 (Symmetry of State Modification and Restoration)

在回溯的「Choose, Explore, Unchoose」三部曲中，狀態的修改與還原必須是**完全對稱、可逆的成對操作**。這確保了當你從一個遞迴分支返回時，狀態能完美地恢復，讓 `for` 迴圈可以正確地探索下一個分支。

**常見的對稱操作：**

| 做出選擇 (Choose)        | 撤銷選擇 (Unchoose)                       |
| :----------------------- | :---------------------------------------- |
| `path.push_back(x)`      | `path.pop_back()`                         |
| `visited[i] = true`      | `visited[i] = false`                      |
| `swap(nums[i], nums[j])` | `swap(nums[i], nums[j])` (再次交換以還原) |
| `count--`                | `count++`                                 |
| `current_sum += x`       | `current_sum -= x`                        |

確保你的每一次狀態修改都有一個對應的、精確的還原操作，是寫對回溯演算法的基礎。

以下是實現「劃分空間」的幾種常見模式：

#### 模式一：使用輔助空間標記 (Auxiliary Space)

- **作法**：使用一個額外的 `bool` 陣列 `visited` 來追蹤哪些元素已經被選入當前的路徑中。
- **優點**：邏輯非常直觀，直接模擬了「這個選項我用過了」的概念。
- **缺點**：需要 `O(N)` 的額外空間。

#### 模式二：傳遞精簡後的選擇集 (Passing Choices)

- **作法**：在每次遞迴呼叫時，只傳遞「尚未被選擇」的元素集。
- **優點**：遞迴函式本身的邏輯最簡單，因為它拿到的永遠是乾淨的選擇集。
- **缺點**：每一次呼叫都可能涉及大量複製，導致時間和空間複雜度過高（例如，在 C++ 中 `vector` 的複製）。
- **實務建議**：在 C++ 等語言中，由於 `vector` 或 `string` 的複製成本很高，**此模式在實務上幾乎不被採用**。它通常只作為一種理論上的思路，或在某些支援高效持久化資料結構的函數式程式語言中有其價值。在面試或競賽中，應優先考慮模式一（輔助空間標記）或模式三（原地操作）。

#### 模式三：原地操作 (In-Place Manipulation)

這是最高級、空間效率最好的技巧。它不依賴額外的追蹤陣列，而是透過直接修改輸入資料（或其副本）的結構來隱性地劃分「已決策」和「待決策」空間。

**經典範例：`swap` + `index` (用於排列問題)**

- **作法**：

  1. 用一個 `index` 變數代表「已決策」空間的邊界。`[0, index-1]` 是已決策的元素。
  2. 在 `for` 迴圈中，將 `index` 位置的元素與後面 `i` 位置的「待決策」元素交換 (`swap(nums[index], nums[i])`)。這個 `swap` 的動作，就是將一個「待決策」元素帶入「當前決策點」。
  3. 遞迴呼叫 `index + 1`，代表「已決策」空間擴大一格。
  4. 回溯時，再次 `swap` 回來，恢復狀態，以便 `for` 迴圈的下一次迭代。

- **心法**：**`swap` 操作是在固定當前決策位置的同時，將整個「待決策」空間的元素輪流推上決策點的方式。** 這種技巧將空間複雜度降至 `O(1)`（若不計遞迴堆疊）。

## 解構建的策略 (Solution Building)

解構建的目標是：在遞迴的過程中，如何以及在何處收集所有找到的有效解。核心的區別在於**解是在決策樹的何處被認定的**。

### 策略一：在葉節點收集解 (Solutions at Leaf Nodes)

- **判斷時機**：當一個**完整的決策路徑**（通常是從根到葉）才構成一個有效的解時，採用此策略。部分路徑本身不是解。
- **作法**：在遞迴的**終止條件 (base case)** 內部，當你確認一個完整的解已經形成時，才將當前的 `path` 複製一份並存入 `results` 容器。
- **結果容器**：`results` 容器通常是透過**傳遞引用 (pass-by-reference)** 或作為**類別成員變數**來在整個遞迴過程中共享。
- **適用問題**：
  - **排列 (Permutations)**: `path` 的長度達到 `n`。
  - **組合 (Combinations)**: `path` 的長度達到 `k`。
  - **N-皇后 (N-Queens)**: 已經成功放置了 `n` 個皇后。

### 策略二：在所有節點收集解 (Solutions at All Nodes)

- **判斷時機**：當**決策過程中的每一個中間步驟（部分路徑）本身就是一個有效的解**時，採用此策略。
- **作法**：在遞迴函式的**入口處**，就立刻將當前的 `path` 複製一份並存入 `results`。這確保了從空集到最長路徑的所有中間狀態都被收集。
- **適用問題**：
  - **子集 (Subsets / Power Set)**: `[]`, `[1]`, `[1, 2]` 等都是合法的子集。

### 區別：回溯 vs. 分治 (Backtracking vs. Divide and Conquer)

需要注意的是，還存在一種看似相似但本質不同的模式：**回傳並組合子問題的解**。

- **作法**：遞迴函式**返回**一個包含其所有子問題解的容器 (`vector<T>`)。上層函式接收來自子節點的解集合，並將其組合、加工成自己的解集再返回。
- **本質**：這更偏向於**分治法 (Divide and Conquer)** 的思想。它不是在維護一個全域的 `path`，而是在每一層獨立地建構解。
- **適用問題**：
  - **Unique Binary Search Trees II**: 遞迴地產生所有可能的左子樹和右子樹，然後在當前層將它們組合起來。
  - 許多純粹的遞迴問題。

## 總結

在設計回溯演算法時，你可以將**狀態管理**和**解構建**作為兩個獨立的設計維度來考慮：

1. **思考狀態管理**：我應該如何最有效地追蹤「已選」和「未選」？是空間換直觀 (`visited` 陣列)，還是用原地操作換效率 (`swap` 技巧)？
2. **思考解構建**：我的問題是「一條路走到黑就是一個解」，還是「需要匯集所有孩子的解」？這決定了你是在 base case `push_back`，還是讓遞迴函式 `return` 一個集合。

清晰地分離這兩個概念，能讓你更有條理地設計出簡潔、高效且正確的回溯程式碼。
