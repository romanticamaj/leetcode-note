# 從不變量倒推 Guard（Guards from Invariants）

> **邊界條件靠猜，不變量可以推。**

Backtracking 寫起來沒把握，幾乎都卡在同一件事：`if` 要放哪些條件、終止條件要寫什麼，全憑感覺試，過了就當對了。

這篇講的心法只有一句：**backtracking 的 guard 不是「邊界條件」，是不變量（invariant）的守衛。** 先把不變量寫下來，所有 guard 和終止條件都是從它機械推出來的，沒有一個需要猜。

> 上一層的原則：不變量是**由構造保證正確**的手段之一——見 [`Design_Principles/Correct_by_Construction.md`](../Design_Principles/Correct_by_Construction.md)。沒有狀態可講的場合（例如 stack 吐出運算元的順序），得改用命名或型別來承載。

---

## 🧠 什麼是這裡的不變量

一句**在遞迴的每個節點都必須為真**的話，描述「什麼樣的部分解**還有救**」。

寫不變量時最常見的來源：**把題目的「合法」定義改寫成前綴形式**。題目說的是「完整的解要滿足 X」，你要問的是「**一個還沒完成的部分解，滿足什麼條件時仍有可能長成合法解**」。這兩者往往長得不一樣，而後者才是不變量。

---

## 🧩 三件事同時被決定

| 要決定的東西 | 怎麼從不變量推出來 |
| :--- | :--- |
| **加某個候選前的 guard** | 「**加完之後不變量還成立嗎？**」不成立就不能加 |
| **終止 / 收集解的條件** | 「**不變量飽和了嗎？**」——所有不等式都取到等號、所有待決策項都決策完 |
| **要不要寫這個防禦性 `if`** | 不變量已經保證的事，**不要再檢查一次**（見下方 ⚠️） |

第二列值得單獨強調：

> **終止條件不是第四個要設計的東西，它是不變量的推論。**

很多人把「guard」和「終止條件」當成兩件獨立的事分別去想，於是終止條件只能靠試。實際上它們來自同一個源頭——guard 維持不變量不被打破，終止條件宣告不變量已經**用滿**。

---

## 📐 標準流程

```cpp
// 寫 code 之前，先寫這幾行（註解留著，不要刪）
// INVARIANT 1: <部分解仍有救的條件，通常是合法性的前綴版本>
// INVARIANT 2: <額外施加的約束，例如為了去重>

void backtrack(State& st, Path& path) {
    if (/* 不變量飽和 */) {
        collect(path);
        return;
    }

    for (const auto& c : candidates(st)) {
        if (/* 加入 c 之後，某條不變量會被破壞 */) continue;  // ← 由不變量倒推

        apply(st, path, c);
        backtrack(st, path);
        undo(st, path, c);
    }
}
```

推導的動作永遠是同一句話：**假設現在不變量成立，加入候選 `c` 之後它還成立嗎？** 把「還成立」的條件解出來，那就是 guard。

### 兩種不同來源的不變量

| 來源 | 性質 | 例子型態 |
| :--- | :--- | :--- |
| **題目的合法性** | 非有不可，少了就會產出錯誤的解 | 「任何前綴都必須滿足某個平衡 / 順序 / 容量條件」 |
| **你額外施加的** | 題目沒要求，是為了**讓每個解只被生成一次** | 「選取的索引必須不遞減」、「相同元素只在第一次出現時分支」 |

兩者都寫成不變量，都用同一個方式倒推出 guard。去重型的細節見 [Duplicate_Removal_Pruning_Design.md](Duplicate_Removal_Pruning_Design.md)。

## 🔁 遞迴參數也是不變量推出來的

不只 guard 和終止條件——**傳給下一層的參數傳什麼，同樣由「你要維持哪條不變量」決定**。

最常被當成隨手決定的 `dfs(i)` vs `dfs(i + 1)`，其實是兩條不同的不變量：

| 不變量 | 遞迴怎麼傳 | 為什麼 |
| :--- | :--- | :--- |
| 選取的索引**嚴格遞增** | `dfs(i + 1)` | 同一個元素不能再用 |
| 選取的索引**非遞減** | `dfs(i)` | 同一個元素允許重複使用 |
| 不限制順序，改用「每個元素只用一次」 | `dfs(0)` + `used[]` | 排列型：順序本身是答案的一部分，遞增限制會殺掉合法解 |
| 切出的段落必須**連續覆蓋**輸入 | `dfs(end)` | 下一段必須從這一段的結尾接上，中間不能有洞 |

前兩列差一個 `+1`，看起來像 off-by-one，實際上是**規格變更**：從「嚴格遞增」放寬成「非遞減」。後兩列比較不直觀，展開說明：

### 第三列：順序本身是答案的一部分

當 `[1,2]` 和 `[2,1]` **都算答案**時（排列型），「索引遞增」這條不變量會**殺掉合法解**——選了後面的元素就不准回頭選前面的。於是不變量換成「每個元素恰好用一次」，守衛也跟著換：

```cpp
for (int i = 0; i < n; i++) {   // 每層都從 0 開始掃全部
    if (used[i]) continue;      // 守衛換成 used[]
    used[i] = true;  path.push_back(nums[i]);
    dfs(...);                   // 不傳 start，因為沒有遞增限制
    path.pop_back(); used[i] = false;
}
```

| | 組合 / 子集 | 排列 |
| :--- | :--- | :--- |
| 順序算不算不同答案 | **不算** → 壓成一種寫法 | **算** → 不能壓 |
| 不變量 | 索引嚴格遞增 | 每個元素恰用一次 |
| 守衛 | 迴圈從 `start` 起 | `used[i]` |
| 傳什麼 | `i + 1` | 不傳（每層從 0） |

### 第四列：前進的距離由 choice 決定

切割型問題的 choice 不是「選哪個元素」，而是「**這一段切到哪裡結束**」：

```cpp
void dfs(const string& s, int start, vector<string>& path) {
    if (start == s.size()) { collect(path); return; }    // 覆蓋完了
    for (int end = start + 1; end <= s.size(); end++) {  // 枚舉這段切到哪
        if (!legal(s, start, end)) continue;
        path.push_back(s.substr(start, end - start));
        dfs(s, end, path);                               // 傳 end，不是 start + 1
        path.pop_back();
    }
}
```

不變量是「**已切出的段落恰好覆蓋 `s[0..start-1]`，不重疊也不留洞**」，所以下一段必須**從這一段的結尾接上**。

與索引遞增型的關鍵差別：**前者每次固定前進一格，後者前進的距離由這次的 choice 決定**——這就是參數不能寫死成 `i + 1` 的原因。這一列也說明遞迴參數**不一定跟去重有關**，這裡守的是**覆蓋的連續性**。

---

> **口訣：參數是不變量的載體。** 不確定該傳什麼，就回去看你寫下的不變量那一行，而不是去想「下一個子問題該從哪開始」。

## ⚠️ 常見陷阱：擋不到的防禦性 guard

當某條不變量已經由「加入前的 guard」維護時，再去檢查「它有沒有被破壞」就是 **dead code**——那條路徑根本不存在，`if` 永遠不會成立。

```cpp
if (count > limit) return;        // ❌ 永遠不會觸發
// ...
if (count < limit) {              // 這行已經保證 count 不可能超過 limit
    apply(); backtrack(); undo();
}
```

> **規則：寫下一個防禦性 `if` 時，先問「什麼路徑會讓它成立？」答不出來就刪掉。**

為什麼要在意這種「無害的冗餘」：

1. 它會讓讀者（和二刷的你）以為存在某條你沒想到的危險路徑，浪費時間去找
2. 面試時它透露**你對自己的不變量沒把握**——擋不到的防禦比沒有防禦更扣分
3. 正確的做法是把它**講出來**而不是寫成 `if`：「因為進入前檢查過 `count < limit`，這裡 `count ≤ limit` 必定成立。」

同一個毛病不限於 backtracking：任何「題目已保證、或前面的邏輯已保證」的條件被再檢查一次，都屬於這一類。

## 💡 副產品：等價的終止條件

終止條件常有好幾種寫法，例如「所有計數都達標」vs「路徑總長度達標」。它們能等價，**靠的正是不變量**。

典型論證形式：若干個量各有上界，而它們的**總和**達到了上界之和，則每一個都必須剛好取到自己的上界。

```
a + b == A + B   且   a ≤ A   且   b ≤ B
⟹ a == A 且 b == B
```

所以「只看總量」的簡寫版本並不是另一種想法，**它只是把不變量已經保證的部分省略不寫**。兩種寫法都對；能講出這段推導，才代表你知道自己為什麼能簡寫。

## ✅ 檢查清單

動手寫 backtracking 之前：

- [ ] 寫下所有不變量（通常 1～3 條），其中一條往往是**題目合法性的前綴版本**
- [ ] 每個候選的 guard，都由「加完之後不變量還成立嗎」推出來
- [ ] 終止條件 = 不變量飽和，不要另外設計
- [ ] 檢查每個 `if`：有沒有哪一個是不變量已經保證的？是就刪掉
- [ ] 去重用的額外約束，也寫成不變量再倒推

## 📚 相關 LeetCode 題型索引

每一列都能用同一個動作解出來：先寫左欄的不變量，guard 從「加完之後還成立嗎」倒推，終止條件 = 不變量飽和。

### 合法性型（不變量來自題目定義）

| 題目 | 不變量 | 倒推出的 guard |
| :--- | :--- | :--- |
| 🔥 **22. Generate Parentheses** | 任何前綴的 `右 ≤ 左`，且 `左 ≤ n` | `left < n` / `right < left` |
| 🔥 **51. N-Queens** | 已放的皇后互不攻擊 | 該行、兩條斜線都未被佔 |
| 🔥 **79. Word Search** | 路徑字元是目標字串的前綴；格子不重走 | 字元相符 + 未走過 + 在界內 |
| **37. Sudoku Solver** | 每行 / 每列 / 每宮不重複 | 三個集合都不含該數字 |
| **131. Palindrome Partitioning** | 已切出的每一段都是回文 | 下一段是回文才切 |
| **93. Restore IP Addresses** | 每段 ≤ 255、無前導零、段數 ≤ 4 | 段值合法 + 剩餘長度夠湊完 |

### 規模 / 容量型（不變量是一條不等式）

| 題目 | 不變量 | 倒推出的 guard |
| :--- | :--- | :--- |
| 🔥 **39. Combination Sum** | `sum(path) ≤ target` | `sum + c ≤ target` |
| **216. Combination Sum III** | `sum ≤ n` 且 `已選個數 ≤ k` | 兩條都不超標 |
| **77. Combinations** | 已選個數 ≤ k，且**剩餘可選數量足夠補滿** | `i ≤ n - (k - path.size()) + 1` |

> 77 的第二條不變量是很好的示範：**「剩下的還夠不夠」也是一條不變量**，它剪掉的是「怎麼選都湊不滿」的整片子樹。

### 去重型（不變量是自己額外施加的）

| 題目 | 額外施加的不變量 | 倒推出的 guard |
| :--- | :--- | :--- |
| 🔥 **46. Permutations** | 路徑上元素互不重複 | `!used[i]` |
| 🔥 **78. Subsets** | 選取的索引嚴格遞增 | 迴圈從 `start` 起 |
| **47. Permutations II** | 相同元素之間固定使用順序 | 排序後 `i>0 && a[i]==a[i-1] && !used[i-1]` 則跳過 |
| **40 / 90. Combination Sum II / Subsets II** | 同一層不重複使用相同的值 | 排序後 `i > start && a[i] == a[i-1]` 則跳過 |

> 這一組的不變量**不是題目要求的**，是為了讓每個解只被生成一次而自己加的。若能改用「結構上不可能重複」的分解方式，就連 guard 都不需要 → 見 [../Divide_and_Conquer/08_Canonical_Anchor_Decomposition.md](../Divide_and_Conquer/08_Canonical_Anchor_Decomposition.md)。
