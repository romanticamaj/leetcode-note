# 練習心法：設計 Test Case 很重要！！！

解題時遵循結構化的思考過程可以幫助我們更系統地解決問題，而設計良好的測試用例是確保解決方案正確性的關鍵。

## 思路步驟

1. **OBSERVATION — 必須留下一行 `ANSWER`**

   「仔細觀察問題」執行不了，因為它沒有產出物，做完也不知道自己有沒有做。改成**動手前先寫下一行註解**（30 秒，寫在 code 上方）：

   ```cpp
   // ANSWER : 把「答案是什麼」寫成可以直接檢查或計算的條件
   ```

   > **⭐ 完成標準：`ANSWER` 裡不能出現題目自己的關鍵詞**（valid、balanced、happy、包含…）。要把它展開成可以直接檢查或計算的條件；展開不了，就代表還沒讀懂題目——這時候想到的任何解法都是猜的。

   沒展開的 `ANSWER` 只是把題目換句話說，擋不到任何錯。36 寫成「board 是否 valid」，就擋不住把 valid 理解成「可解」；展開成「每一行、列、宮裡，已填的數字都不重複」，backtracking 就明顯不需要。

   `ANSWER` 是一個**靶**。沒有靶就選解法，選得再快也無從檢驗；真正的失誤通常不是「選錯演算法」，而是「在還沒立靶之前就開始射」。

   | 題目 | 沒展開（沒用） | 展開後的 `ANSWER` | 少寫它的代價 |
   | :--- | :--- | :--- | :--- |
   | 36 Valid Sudoku | board 是否 valid | 每一行、列、宮裡，已填的數字都不重複 | 把 valid 當成「可解」，跳去 backtracking |
   | 15 3Sum | 找三個數和為 0 | 回傳所有不重複的**值**三元組 `(a, b, c)`，`a + b + c = 0` | 把回傳值誤會成 index |
   | 543 Diameter | 樹的直徑 | 對某個節點 v，`左深 + 右深` 的最大值 | 誤以為路徑一定經過 root |
   | 238 Product Except Self | 除了自己以外的乘積 | `ans[i] = (左邊全部乘積) × (右邊全部乘積)` | 想不到 prefix/suffix，繞去 D&C |
   | 19 Remove Nth From End | 刪掉倒數第 k 個 | 刪掉第 `n - k + 1` 個節點後的 list | 看不出 `n` 是唯一未知數，錯過 one-pass 的目標 |
   | 76 Minimum Window Substring | 包含 `t` 的最短子字串 | 每個字元在窗口裡的數量 ≥ 在 `t` 裡的數量，其中最短的 | 看不出 constraint metric 要追蹤什麼 |

   展開後的 `ANSWER` 有兩個用途：

   - **它就是 brute force**：照字面檢查這個條件，就是暴力解，第 2 步直接從這一行接下去
   - **優化是機械的下一步**：看式子裡哪一項被重複計算、可以預先算好，哪個未知數可以消掉

   **另外兩行，只在有觸發條件時才寫：**

   ```cpp
   // IN/OUT : 回傳型別不明顯時（index 還是值？一組還是全部？找不到回傳什麼？）
   // LIMIT  : 題目有禁止事項時（in-place、O(1) space、不能用除法…）
   ```

   通常 `ANSWER` 展開得夠完整，回傳型別就已經包含在內（例如 3Sum 那一行），不用另寫 `IN/OUT`。

   > **[黃金法則] 演算法卡住時，就找具體的例子來驗證，不要乾想浪費時間。**
   > 手動模擬一個簡單的例子，觀察其決策過程與狀態變化，能幫助你快速找到規律，打破僵局。

2. **BRUTE FORCE + 時間分析**

   - 首先考慮最直接的解決方案
   - 分析暴力解法的時間和空間複雜度
   - 識別可能的瓶頸和優化機會

   > **⚠️ 為什麼不能跳過暴力解：暴力解是規格的可執行版本。**
   > 它的用途不是「當優化的起點」，而是**確認你理解的題目是對的**。跳過 brute force，等於跳過「我有沒有讀懂題目」這道驗證。
   >
   > 練習時**依序「想」、不必依序「寫」**：brute force 口頭成立就夠，手寫留給最佳解。面試時則**一定要依序講**，但 brute force 用 15 秒帶過並指出它的弱點——面試官買的是「你怎麼從 A 走到 B」，不是 B 本身。

3. **使用技巧優化, 指出實作重點**

   - 應用適當的算法技巧（如 **Sliding Window**、**Prefix Sum**、**Two Pointers** 等）來優化解決方案
   - 強調實現中的關鍵點和潛在的陷阱
   - 考慮邊界情況和特殊輸入

4. **使用 test case 確認 — 手動 dry run**

   > **⭐ 寫完不等於寫對。程式寫完的那一刻，你唯一還握得住的浮木，是親手把一個 test case 走一遍。**

   - **為什麼重讀程式碼救不了你：** 讀自己的 code 時，你是用「**我以為它在做什麼**」去讀，不是用「它實際上做什麼」去讀。兩者一致才是特例。**dry run 強迫你用機器的方式讀它**——這是唯一能拆穿那個落差的動作。
   - **挑哪個 case：** 不是隨便挑，也不是挑最大的。挑**最小的、剛好能打到你最沒把握那條分支**的那個。心裡有「這裡我有點虛」的地方，就是它該瞄準的地方。
   - **最低標準：至少跑兩個——一個 classic、一個 edge。** 兩個抓的是不同種類的 bug，少跑哪一個就漏哪一類：
     - **classic**（題目範例那種典型輸入）→ 驗證**主邏輯**：轉移式、合併、指標移動方向對不對。
     - **edge**（空、單一元素、全相同、已排序 / 沒旋轉、答案在最邊邊）→ 驗證**邊界與初值**：base case、迴圈起訖、`dp` 初值、sentinel。上面說的「最沒把握那條分支」通常就是這一個。
     - 只跑 classic 是最常見的假安全感：主邏輯對了，但初值或邊界錯的 code **在典型輸入上照樣會過**（例：LC 300 回傳 `dp[n-1]` 而非 `max(dp)`，題目範例 `[10,9,2,5,3,7,101,18]` 剛好會過，`[1,2,3,0]` 才爆；LC 153 拿左端當參照又沒有「已排序」特判，旋轉過的範例都過，沒旋轉的 `[1,2,3]` 才爆）。
   > 補一句反面的：**「看起來對」不是證據，「跑起來對」才是。** 而在面試裡沒有編譯器，所以「跑」只能靠手——這讓 dry run 從好習慣升級成唯一手段。

## 解題前的關鍵假設檢查

在開始解題之前，檢查和理解題目的隱含假設是非常重要的。忽略這些假設可能導致解法錯誤或不必要的複雜性。

### 1. 輸入數據特性假設

**問題描述**：許多算法題目對輸入數據有隱含假設，但這些假設可能沒有明確說明。

**需要考慮的關鍵假設**：

- 輸入是否包含重複元素（distinct vs. duplicate）
- 輸入是否已排序
- 輸入是否可能為空
- 輸入數據的範圍（可能影響溢出處理）
- 輸入是否包含負數（對於某些算法很重要）

**錯誤示例**：

```cpp
// 錯誤示例 - 假設輸入沒有重複元素
vector<int> nums = {1, 2, 2, 3, 4};
unordered_set<int> numSet(nums.begin(), nums.end());
if (numSet.size() != nums.size()) {
    // 這個條件會為真，因為有重複元素
    // 但如果算法假設輸入沒有重複，可能會導致錯誤
}
```

**正確示例**：

```cpp
// 正確示例 - 明確檢查重複元素
vector<int> nums = {1, 2, 2, 3, 4};
unordered_set<int> numSet;
bool hasDuplicates = false;
for (int num : nums) {
    if (!numSet.insert(num).second) {
        hasDuplicates = true;
        break;
    }
}
// 根據是否有重複元素選擇不同的算法
```

**避免方法**：

1. 仔細閱讀題目，識別明確和隱含的假設
2. 考慮極端情況和邊界條件
3. 在代碼中添加檢查，驗證關鍵假設
4. 如果假設不明確，考慮多種可能性或在解題前澄清

### 2. 其他常見假設

- **數據結構特性**：例如，二叉樹是否平衡，圖是否有環
- **操作限制**：是否有時間或空間複雜度要求
- **返回值要求**：返回實際值還是索引，多解時返回任意解還是特定解
- **修改輸入**：是否允許修改原始輸入數據

在解題過程中，明確這些假設可以幫助你選擇正確的算法和數據結構，避免不必要的錯誤和優化。
