# 解題思路、觀念與想法

本文件收集各種解題的關鍵思路、觀念和想法，幫助更有效地解決算法問題。

## 🧭 解題指北星：先建立 Brute Force，再用 BUD 與 BCR 推進

> **先能說清楚一個正確的 brute force，才有具體的工作可分析、可優化。練習的第一個反射：最直接怎麼做？接著才問：哪些工作可以省掉，離合理的最佳時間還有多遠？**

Brute force 同時是題意的可執行驗證，以及優化的基準。至少要說清楚：枚舉什麼、怎麼判定或計算答案、為什麼不漏解，以及時間／空間複雜度。只有「用 DFS」或「全部試一次」還不夠具體。

| 階段 | 要回答的問題 | 產出 |
| :--- | :--- | :--- |
| **Brute Force** | 最直接且正確的方法怎麼做？ | 可 dry run 的流程或 pseudocode，以及複雜度 |
| **BUD** | 瓶頸在哪？哪些工作不必要？哪些工作重複？ | 指出原解法中具體要減少的工作 |
| **BCR**（Best Conceivable Runtime） | 哪些成本無法省？合理的最佳時間目標是什麼？ | 根據輸入、輸出與必要操作估計下限，對照目前成本 |
| **優化與驗證** | 用什麼性質或工具消掉那些工作？ | 保持正確性的理由、新複雜度，以及仍然存在的差距 |

BUD 找改善的位置，BCR 幫助判斷改善的空間；兩者可以反覆對照。例如列舉全部答案時，輸出本身可能已是指數級，不能因為加了 cache 就期待總時間變成多項式。BCR 的估計要交代依據；沒有下界證明時，不把猜到的目標當成已證明的最優複雜度。

**練習反射：Brute Force → 分析成本 → BUD ↔ BCR → 優化 → 驗證。** 不必每題先實作暴力版，但必須能具體描述並驗證；若連暴力版都想不出來，先回到答案定義、候選選擇與完整枚舉，讓優化有根據。

如何建立這個基準，見 [暴力法設計與 BUD 優化心法](../Algorithms/Brute_Force/README.md)：從自己看、固定部分選擇、枚舉邊界、逐步決策、指定參數與直接模擬，建立可驗證的基準，再辨認要消除的工作。

## 核心解題觀念

### 沒想清楚前，不用下手 coding

在完全理解問題本質和設計出清晰解法之前，不要急於開始寫代碼。

### LeetCode 練習先提交，確認第一版解法正確，再來想 followup

在 LeetCode 練習時，先專注於實現一個正確的基礎解法並通過測試，之後再考慮優化和各種 follow-up 問題。

### BUD Optimization

針對演算法進行優化時，系統性地檢查三個方向：Bottlenecks（瓶頸）、Unnecessary work（不必要的工作）、Duplicated work（重複的工作）。

> **卡住時該問的不是「該用什麼資料結構」，是「哪些工作重複了」。**

這兩個問題的差別在於**有沒有方向**。問資料結構，只能靠回想題型標籤去猜（而且 tag 給的路線常常又對又繞）；問重複工作，是對著自己剛寫出來的解法做**可執行的檢查**，答案直接指向該消掉什麼。

實務上的順序是：**先建立可驗證的暴力解 → 指出具體的瓶頸、不必要或重複工作 → 才去問「什麼工具能減少這些工作」**。不必先實作暴力版，但要能 dry run；工具的選擇要對應已識別的成本。

**重複也可能是完整狀態序列。** 若同一完整狀態的下一步唯一確定，重遇狀態代表後面的演化將重播，可跳過整個週期，而不是只加速單步。LC 957 的推導與模板見 [Cycle Detection + Fast Forwarding](../Algorithms/Simulation/02-Cycle_Detection_and_Fast_Forward.md)。

### 使用不同的視角切入題目

重新表述或轉換問題的角度，可以讓難題變得更容易解決。

### 避免「單一範例陷阱」

不要讓題目給定的單一範例限制你的思路，應該主動構造反例並回歸問題本質，確保解法能處理所有符合約束的輸入。

### 不要落入記憶陷阱，專注演算法正確性思考、專注 Conceptual Thinking

遇到似曾相識的題目時，不要急於套用記憶中的解法或模板。應該從演算法的核心概念和原理重新推導，確保每一步的邏輯正確性。
記憶可能不完整或有誤，而概念性思考 (Conceptual Thinking) 能應對題目的細節變化和 follow-up 問題。
