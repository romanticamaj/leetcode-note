# PACELC 定理：CAP 的延伸

CAP 定理很好地解釋了在「網路分區」發生時系統必須做的權衡。然而，它沒有描述在系統**正常運行**時（沒有分區）的行為。

**PACELC 定理** 正是為此而生，它更完整地描述了分散式系統的權衡。

**PACELC** 的意思是：

- **If** there is a **P**artition (如果發生網路分區),
- **then** a system must choose between **A**vailability and **C**onsistency (系統必須在可用性和一致性之間做選擇).
- **Else** (否則，當系統正常運行時),
- **then** a system must choose between **L**atency and **C**onsistency (系統必須在延遲和一致性之間做選擇).

---

## E - Else: 延遲 (L) 與 一致性 (C) 的權衡

當系統沒有網路分區時，所有節點都可以正常通訊。此時，設計者面臨一個新的權衡：

- **選擇 Latency (L) - 低延遲**：

  - **策略**：為了讓使用者請求得到最快的回應，系統可能會從最近的節點直接回傳資料，即使這份資料可能不是全局最新的。
  - **行為**：寫入操作可能只需要更新一部分節點（例如，寫入本地節點後立即返回成功），然後非同步地將更新傳播到其他節點。這降低了寫入延遲。讀取操作也可能只查詢最近的節點。
  - **結果**：犧牲了強一致性，換取了更低的操作延遲。

- **選擇 Consistency (C) - 強一致性**：
  - **策略**：為了保證每次讀取都返回最新的資料，系統必須犧牲延遲。
  - **行為**：寫入操作必須等待，直到資料被同步到所有（或大多數）副本節點後，才能向客戶端確認寫入成功。這個同步過程（例如，使用 2PC 或 Paxos/Raft 等共識演算法）會增加延遲。
  - **結果**：犧牲了低延遲，換取了更強的資料一致性。

---

## PACELC 系統分類

PACELC 定理提供了一個更細緻的分類框架：

- **PA/EL (Availability/Latency)**:

  - **描述**: 系統在分區時選擇**可用性**，正常時選擇**低延遲**。
  - **代表**:
    - **DynamoDB**, **Cassandra**: 這些系統的設計核心就是高可用和低延遲，它們通常提供可調整的一致性級別，但預設傾向於 AP 和 EL。
    - **Riak**

- **PC/EC (Consistency/Consistency)**:

  - **描述**: 系統在分區時選擇**一致性**，正常時也選擇**一致性**。
  - **代表**:
    - **傳統關聯式資料庫** (如 MySQL, PostgreSQL) 的叢集：它們總是優先保證資料的 ACID 特性。
    - **HBase**, **BigTable**
    - **MongoDB** (在較新版本中，預設配置越來越傾向於強一致性)

- **PA/EC (Availability/Consistency)**:
  - **描述**: 系統在分區時選擇**可用性**，正常時選擇**一致性**。
  - **代表**:
    - **PNUTS** (Yahoo! 的系統)

---

## 🧠 總結

- **PACELC** 是對 **CAP** 的一個重要補充，它指出了在系統正常運行時，**延遲 (Latency)** 和 **一致性 (Consistency)** 之間存在著固有的權衡。
- CAP 關注的是「系統故障時怎麼辦」，而 PACELC 的 `Else` 部分關注的是「系統平時如何表現」。
- 理解 PACELC 有助於更全面地評估和選擇適合特定業務場景的分散式系統。
